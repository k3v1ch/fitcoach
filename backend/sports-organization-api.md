# Спортивная организация

## Техническая документация и API

**Редакция:** 2 октября 2026 · **API:** `/api/v1` · **71 реализованная операция**

Веб-приложение для учёта спортсменов, расписания, посещаемости, результатов, документов и ручных платежей.

> **Регистрация**  
> Email → ссылка в письме → подтверждение имени и пароля → вход.

Этот документ объединяет целевые требования и описание проекта. В исходниках сейчас реализована 71 HTTP-операция; из 79 методов в разделе API восемь пока не реализованы. Их статус указан в соответствующих описаниях. Для точного контракта работающих маршрутов используйте OpenAPI по `/v3/api-docs`.

**Регистрация в текущем проекте**

- `POST /auth/register` принимает `email`, а также необязательные `accountType` и `fullName`.
- `POST /auth/register/confirm` требует `token`, `fullName` и `password`; тип аккаунта можно указать повторно.
- Телефон текущий API регистрации не принимает и в профиле аккаунта не хранится.
- Подробный контракт регистрации в разделах ниже следует считать целевым там, где он расходится с текущими DTO и OpenAPI.

Глобальная роль аккаунта в проекте — `USER`. Роли `TRAINER`, `PARENT`, `ATHLETE` и `AGENCY` относятся к членству в организации. Создатель организации автоматически получает роль `TRAINER`; тренер также может добавить в организацию родителя или спортсмена по email. Общего API для произвольного назначения и редактирования членств и прав нет.

**Запуск проекта**

```powershell
Copy-Item .env.example .env
docker compose up --build
```

API: `http://localhost:8080`; Swagger UI: `http://localhost:8080/swagger-ui.html`; OpenAPI JSON: `http://localhost:8080/v3/api-docs`. PostgreSQL и API запускаются сервисами Docker Compose, данные БД и загруженные файлы сохраняются в volumes.

**Как читать документ:** заголовки обозначают разделы и методы; `моноширинный текст` — поля, пути и значения API; **жирный текст** — обязательность и ключевые условия. В таблицах моделей обязательность относится к запросам. В ответах присутствуют все описанные поля.

## 1. Общие требования

**Серверная часть**

Сервер разрабатывается на Java Spring Boot. Данные хранятся в PostgreSQL. Интерфейс получает и изменяет данные через HTTP API в формате `JSON`; для загрузки файлов используется multipart/form-data.

**Организации**

Один пользователь может состоять в нескольких организациях. В запросе указывается `organizationId` — организация, с которой он сейчас работает. Данные одной организации недоступны участникам другой.

**Начальная настройка**

PostgreSQL и приложение запускаются через Docker Compose. Авторизованный пользователь может создать организацию через API; его активное членство `TRAINER` создаётся в той же транзакции. Начальные справочники загружаются миграциями.

**Нормативы и разряды**

Нормативы и разряды доступны только для просмотра. Примеры записей загружаются вместе с начальными данными. Ввод и редактирование через сайт не предусмотрены.

## 2. Роли и права доступа

**Роли**

В приложении глобальная роль аккаунта — `USER`. `TRAINER` — тренер, `PARENT` — родитель, `ATHLETE` — спортсмен, `AGENCY` — председатель организации. Эти роли относятся к Membership и назначаются в контексте организации. Membership содержит роли, права и статус доступа.

**Назначение доступа**

Создатель организации автоматически становится её тренером с полными правами. Тренер с `members.write` может добавить активированный аккаунт родителя в свою организацию по email. Произвольный поиск аккаунтов и свободное назначение или изменение произвольных ролей и прав не предоставляются.

**Тренер**

`TRAINER` просматривает данные своей организации и меняет их в пределах выданных прав. Поле `coachIds` у группы и тренировки указывает ответственных тренеров. Оно используется в расписании и фильтрах, но не ограничивает доступ только собственными группами.

**Председатель**

`AGENCY` может просматривать данные своей организации и выгружать отчёты. Изменять записи, загружать документы, отвечать на объявления и отмечать их прочтение ему нельзя. `AGENCY` не совмещается с другими ролями в той же организации. Вход, выход и смена своего пароля доступны.

**Родитель и спортсмен**

`PARENT` видит данные своих детей, `ATHLETE` — свои данные. Им доступны связанные группы, занятия, результаты, документы и начисления. Они могут загружать документы и отвечать на адресованные им объявления и мероприятия. Связь родителя с ребёнком задаёт тренер с правами `athletes.write` и `members.write`.

**Совмещение ролей**

`TRAINER`, `PARENT` и `ATHLETE` можно совмещать. Действие разрешается, если хотя бы одна роль позволяет его выполнить для выбранных данных и у пользователя есть нужное право. После снятия роли связанные записи сохраняются, но больше не дают доступа.

**Проверка прав**

Сервер проверяет права при каждом запросе. Список организаций, ролей и прав возвращает `GET /organizations`; `/me` содержит только данные аккаунта и срок сессии.

**Права на просмотр**

`members.read`, `sections.read`, `groups.read`, `athletes.read`, `schedule.read`, `trainingReports`.read, `attendance.read`, `progress.read`, `events.read`, `announcements.read`, `documents.read`, `charges.read`, `payments.read`, `finance.read`, `reports.read`. Просмотр своих ролей, сведений об организации и общих справочников доступен любому активному участнику организации.

**Права на изменение**

`organization.write`, `members.write`, `sections.write`, `groups.write`, `athletes.write`, `schedule.write`, `trainingReports`.write, `attendance.write`, `progress.write`, `events.write`, `announcements.write`, `documents.write`, `charges.write`, `payments.write`, `dictionaries.write`. Свободного маршрута назначения прав нет. `members.write` позволяет тренеру добавлять родителя и связывать его со спортсменами.

**Права для разных ролей**

`TRAINER` можно назначить любые перечисленные права. `AGENCY` — только права .read и `reports.export`. `PARENT` и `ATHLETE` — `sections.read`, `groups.read`, `athletes.read`, `schedule.read`, `trainingReports`.read, `attendance.read`, `progress.read`, `events.read`, `announcements.read`, `documents.read`, `charges.read`, `payments.read`, `reports.read` и `reports.export`. Для них права действуют только на свои данные. Загрузка своих документов и ответы разрешены по роли и связи с записью, без общего права .write. При совмещении ролей можно назначить права любой из них. Попытка назначить недопустимое право возвращает 400.

**Выгрузка отчётов**

Для выгрузки нужны `reports.read`, `reports.export` и право чтения данных, по которым строится отчёт.

**Проверка организации**

Сервер проверяет `organizationId` и все связанные идентификаторы: спортсмена, группы, мероприятия, файла и другие. Если запись относится к другой организации, возвращается 404. Это правило действует также для списков, итоговых сумм и выгрузок.

## 3. Функции приложения

**Регистрация**

`POST /auth/register` принимает `email`, необязательные `accountType` и `fullName`. По ссылке из письма пользователь отправляет `token`, обязательные `fullName` и `password` в `POST /auth/register/confirm`; телефон этот API не принимает. После подтверждения пользователь входит и может создать организацию; при создании ему автоматически выдаётся членство тренера.

**Добавление пользователей**

Создание и изменение карточек спортсменов доступны через методы организации. При создании карточки можно связать её с аккаунтом `ATHLETE`, если у него уже есть активная роль в этой организации. Тренер может добавить активированный аккаунт родителя по email и затем связать его с карточкой ребёнка.

**Тренировки**

Тренер создаёт секции, группы и расписание. У тренировки есть время, место, ответственные тренеры и план с этапами. После занятия тренер отмечает посещаемость и заполняет отчёт. Закрытый отчёт переводит тренировку в `COMPLETED`. Менять его и посещаемость после этого нельзя. Отменённая тренировка не закрывается; начисления при отмене автоматически не меняются.

**Результаты**

Тренер записывает показатель, значение, единицу измерения, дату и комментарий. Личный рекорд отмечается вручную полем `isPersonalBest`. Для графика используются результаты одного показателя с одинаковой единицей измерения.

**Мероприятия**

Тренер создаёт черновик мероприятия, добавляет участников и публикует его. Родитель или спортсмен отвечает за свою карточку и прикладывает нужные документы. Тренер и председатель видят ответы в пределах своих прав. Начисления за участие создаются вручную.

**Денежные сборы**

`CAMP` обозначает учебно-тренировочный сбор, `FUNDRAISER` — сбор денег на определённую цель. У `FUNDRAISER` указываются сумма и срок. Для каждого участника тренер создаёт начисление type = `EVENT` с `eventId` этого сбора. В списке начислений видны взносы и долги, а общая сумма сбора считается по действующим платежам.

**Оплата**

Деньги передаются вне приложения. Тренер записывает начисление и полученный платёж. Разрешена частичная оплата, но сумма платежа не должна превышать остаток долга. Ошибочный платёж аннулируется с указанием причины; затем можно внести правильный. Приложение не переводит и не возвращает деньги, не учитывает расходы, авансы и переплаты.

**Объявления**

Тренер пишет объявление, выбирает получателей и добавляет вложения. При необходимости можно запросить согласие. Получатели отмечают прочтение и отвечают; ответы сохраняются в истории.

**Председатель только просматривает данные**

После публикации текст и список получателей менять нельзя.

**Документы**

Документ относится к спортсмену или организации. Для него указываются тип, дата выдачи и срок действия. По сроку можно найти просроченные документы. Медицинская справка хранится как документ; допуск спортсмена по ней не рассчитывается.

**Поиск**

Поиск q работает внутри списков пользователей, участников, спортсменов, родителей, секций, групп, тренировок, мероприятий, объявлений, документов, начислений и справочников.

**Отчёты**

Предусмотрены отчёты по посещаемости `ATTENDANCE`, тренировкам `TRAININGS`, результатам `PROGRESS` и начислениям `CHARGES`. В текущем проекте отчёты можно просматривать и экспортировать только в CSV; PDF и XLSX остаются целевыми форматами. В отчёт попадают только доступные пользователю данные.

## 4. Требования к реализации

**Основные данные**

User хранит аккаунт, Organization — организацию, Membership — участие пользователя и его права. Athlete хранит карточку спортсмена, ParentLink — связь с родителем. Section, Group и GroupAthlete описывают секции, группы и историю состава. Training, TrainingReport, Attendance и Result хранят занятия, отчёты, посещаемость и результаты. Для остальных разделов используются Event, EventParticipant, Announcement, ответы и получатели объявлений, Document, File, Charge, Payment и DictionaryItem. У незавершённой регистрации User.`fullName` и хеш пароля допускают `null`; активация требует заполненного имени и хеша пароля.

**Итоги и история**

Dashboard, FinanceSummary, EventFinance и отчёты рассчитываются по данным основной базы. Журнал Activity хранит изменения записей, которые пользователь вправе видеть. Пароли и токены в журнал не записываются.

**Тестовые данные**

Для проверки нужны две организации, пользователи с организационными ролями, спортсмен с родителем, группа, тренировка, результаты, норматив и разряд, мероприятие, денежный сбор и начисление. Тестовые учётные данные нельзя использовать на рабочем сервере.

**Справочники**

Редактируются три справочника: sport-types — виды спорта, training-types — типы тренировок, venues — площадки. Типы документов и статусы спортсменов задаются фиксированными значениями в коде.

**Технологии**

Сервер работает как одно приложение Spring Boot. Контроллеры принимают запросы, сервисы проверяют права и выполняют операции, репозитории работают с PostgreSQL. Для миграций используется Flyway, для входа и сессий — Spring Security, для проверки полей — Bean Validation, для писем — SMTP. Версии зависимостей фиксируются в сборке.

**Ограничения базы**

Email после нормализации должен быть уникальным. Для каждой пары `userId`/`organizationId` хранится одна запись Membership и не более одной карточки Athlete. У спортсмена может быть только один незакрытый период участия в одной группе. Для пары `trainingId`/`athleteId` хранится одна отметка посещения, для тренировки — один отчёт. Idempotency-Key платежа уникален в пределах организации. Денежные суммы хранятся в decimal с двумя знаками после запятой.

**Сохранение изменений**

Активация аккаунта, блокировка, назначение доступа, пакет отметок посещения, закрытие отчёта, запись и аннулирование платежа выполняются в транзакции: сохраняются либо все изменения, либо ни одно. Два одновременных платежа не должны превышать остаток долга. Пароли, токены и другие секреты не выдаются в ответах и не записываются в журнал.

**Письма**

Письма отправляются при регистрации и восстановлении пароля через SMTP. Отправку можно выполнять во время запроса с ограничением времени ожидания. Ошибка доставки записывается в журнал без токена. Пользователь может повторить запрос после установленной задержки. Ответ 202 означает, что запрос принят; он не подтверждает доставку письма.

**Файлы и выгрузки**

В текущем проекте экспорт отчётов реализован только в CSV; PDF и XLSX остаются целевыми форматами.

Разрешены PDF, PNG и JPEG до 10 МБ. Файлы хранятся в папке сервера вне публичного каталога, сведения о них — в базе. Выгрузка отчёта выполняется во время запроса и содержит не более 10 000 строк. При превышении лимита сервер просит сузить фильтры.

**Состав проекта**

Проект включает исходный код сервера, настройки запуска без секретов, миграции, тестовые данные, инструкцию по SMTP и хранению файлов, описание API в OpenAPI и проверки основных функций.

## 5. Проверка работы

**Регистрация**

`POST /auth/register` требует `email`, принимает необязательные `accountType` и `fullName`. Подтверждение требует `token`, `fullName` и `password`; `accountType` по умолчанию `ATHLETE`. Телефона в текущем API нет. После входа пользователь может создать организацию; для существующих организаций членство выдаёт тренер через доступные операции или администрирование.

**Доступ**

Запросы к закрытым разделам без входа отклоняются. Пользователь не может получить данные другой организации, подставив её `UUID`. Родитель видит своих детей, спортсмен — себя. Председатель просматривает данные и выгружает отчёты, но не меняет записи. Доступ ограничивается членством в организации и правами; список членств доступен отдельным маршрутом `/organizations`.

**Посещаемость**

Отчёт можно закрыть после окончания тренировки, когда отмечены все участники. После закрытия отчёт и отметки не меняются. Изменение состава группы не влияет на уже сохранённую посещаемость. Отменённые занятия не входят в процент посещения.

**Платежи**

У начисления 1000.00 после оплаты 400.00 остаётся долг 600.00 и статус `PARTIALLY_PAID`. Повтор запроса с тем же ключом не создаёт второй платёж. Платёж 700.00 отклоняется, а 600.00 закрывает долг.

Аннулирование платежа снова увеличивает долг на эту сумму. При одновременных запросах остаток не становится отрицательным.

**Мероприятия**

Для `FUNDRAISER` нужны цель и срок сбора, для обычного мероприятия — место и время.

Собранная сумма совпадает с суммой действующих платежей. Родитель не видит суммы других детей. Завершение или отмена мероприятия не удаляет начисления.

**Файлы и поля**

Файл чужой организации недоступен. Файл неподдерживаемого типа или больше 10 МБ не загружается. Документ виден только пользователю с доступом к его владельцу. Ошибки обязательных полей, неизвестных полей, недопустимых значений и ссылок возвращаются в одном формате.

**Поиск и отчёты**

Поиск и `totalElements` учитывают только доступные записи. В каталоге четыре вида отчётов. CSV-выгрузка совпадает с просмотром при одинаковых фильтрах; формулы из пользовательского текста экранируются. Отображение в PDF/XLSX следует проверить после реализации этих форматов.

**Нормативы и разряды**

Пользователь видит записи из тестовых данных. Изменить их через API нельзя.

## 6. Описание API

**Обозначения**

Path — параметры пути; Query — параметры строки запроса; `JSON` — тело запроса; Header — HTTP-заголовок. Все адреса начинаются с /api/v1. Описание моделей приведено в конце соответствующего раздела API.

### 6.1. Общие правила

**Адреса и типы**

Базовый префикс /api/v1. Все пути `/organizations/{organizationId}/...` требуют `organizationId`. Все параметры *Id в пути — обязательные `UUID`; `dictionaryType` и `reportType` — перечисления. `JSON`: application/json; файлы: multipart/form-data. `GET` не принимает тело.

**Поля**

`*` обозначает обязательное поле запроса. Значение `null` разрешено только там, где это указано. `UUID` — строка; date — `YYYY-MM-DD`; datetime — RFC 3339 со смещением; decimal — `JSON`-число; money — строка суммы в рублях с двумя знаками, например "1250.00". В ответах все описанные поля присутствуют; необязательные значения моделей Write возвращаются как `null`. Звёздочка относится только к запросам.

**Изменение**

`PATCH` принимает хотя бы одно из перечисленных полей. Непереданное поле не меняется. Массив заменяется целиком; исключение — memberships, где записи обновляются по `organizationId`. Неизвестное поле возвращает 400. id, `organizationId`, `createdAt`, `createdBy` и итоговые суммы задаёт сервер.

Связанные записи должны относиться к той же организации. Дата окончания не может быть раньше начала; название не может быть пустым.

**Списки и поиск**

`Page<T>` = {items: T[], page: integer, size: integer, `totalElements`: integer, `totalPages`: integer}. page от 0, по умолчанию 0; size 1–100, по умолчанию 20. q — поиск подстроки без учёта регистра в указанных текстовых полях; пробелы по краям удаляются, пустой q игнорируется. При нескольких фильтрах запись должна подходить под каждый из них. `totalElements` считается после ограничений доступа. Тренировки сортируются по `startsAt`,id, результаты — `measuredOn`,id; остальные списки — `createdAt`,id по убыванию либо id, если `createdAt` отсутствует.

**Сессии**

Cookie HttpOnly, SameSite=Lax; флаг Secure задаётся через `SESSION_COOKIE_SECURE` (в Compose для локального HTTP выключен, за HTTPS в production должен быть включён). Сессия истекает через 8 часов после входа, без продления. Для `POST`/`PUT`/`PATCH`/`DELETE` нужен токен `GET` /auth/csrf и cookie связанной сессии, включая публичную регистрацию и вход. `CSRF` привязан к сессии; после входа клиент получает новый `CSRF`-токен. OpenAPI описывает `JSESSIONID` и `X-CSRF-TOKEN`; Swagger UI и `/v3/api-docs` открыты без авторизации. Пароли: 15–128 символов, без обязательных сочетаний типов символов; хранится только хеш Argon2id. Токены ссылок случайные не менее 256 бит, в базе только хеш, срок и назначение; каждый используется один раз. SMTP настроен переменными окружения, секреты не хранятся в репозитории.

**Проверка доступа**

Для доступа нужны `ACTIVE`-аккаунт с подтверждённым `email`, активное Membership и нужные права. `TRAINER` и `AGENCY` читают данные своей организации в пределах прав. `PARENT` видит своих детей, `ATHLETE` — себя. Для объявлений и мероприятий также проверяются получатели и участники; `TRAINER` и `AGENCY` с правом .read могут просматривать весь доступный раздел. Для вложенных данных, итогов, выгрузок и файлов права проверяются отдельно. `AGENCY` не может менять записи, в том числе свои документы, ответы и отметки прочтения. Ему доступны смена пароля и выход из аккаунта.

**Ошибки**

Формат ошибки:

```text
{code: string, message: string, fieldErrors: {field: string, message: string}[], requestId: string}
```

| HTTP-код | Значение |
| --- | --- |
| **400** | неверные поля |
| **401** | нет сессии |
| **403** | нет права |
| **404** | объект отсутствует или находится вне доступной области |
| **409** | дубликат/конфликт |
| **413** | слишком большой файл |
| **415** | неверный тип |
| **422** | слишком большая выгрузка |
| **429** | частые запросы |
| **200** | чтение/изменение |
| **201** | создание |
| **202** | принят запрос письма |
| **204** | без тела |

**Файлы**

Разрешены PDF, PNG и JPEG до 10 МБ; проверяются расширение, MIME и сигнатура. Файлы хранятся вне публичного web-каталога под серверными именами, скачиваются с Content-Disposition: attachment. Срок `validUntil` относится только к документу и не вычисляет медицинский статус спортсмена.

**Начисления**

`paidAmount` — сумма `ACTIVE`-платежей; `remainingAmount` = amount − `paidAmount`. `UNPAID` при `paidAmount` = 0; `PARTIALLY_PAID` при 0 < `paidAmount` < amount; `PAID` при равенстве. `isOverdue` — `ACTIVE`, остаток > 0 и `dueOn` раньше текущей даты организации. Отменённые начисления и `VOIDED`-платежи не входят в итоги. Присутствие, публикация мероприятия и отмена тренировки сами по себе не создают финансовые записи.

**Время и состав**

Время хранится в UTC и возвращается со смещением. Календарные даты считаются в timezone организации. Для date в период входят обе границы, для datetime используется [from,to). Спортсмен входит в состав занятия, если `joinedOn` не позже даты тренировки, а `leftOn` не указан или не раньше этой даты. После первой отметки посещения состав фиксируется. Последующие изменения группы не меняют этот список.

#### 002. Запросить письмо для начала регистрации

**`POST`** `/auth/register`

**Доступ:** Без входа.

**Параметры запроса**

**Тело · `JSON`**

| Параметр / модель | Тип / условия | Обязательно |
| --- | --- | --- |
| `email` | `string` | **Да** |
| `accountType` | `TRAINER \| ATHLETE \| PARENT` | — |
| `fullName` | `string`, не более 200 символов | — |

**Ответ:** **202** — `{message: string}`

**Правила**

- Email нормализуется и проверяется на корректность.
- Для нового адреса создаётся аккаунт `PENDING_EMAIL`; переданный `fullName` сохраняется, иначе используется пустая строка. Пароль и `emailVerifiedAt` ещё не заданы.
- `accountType` по умолчанию `ATHLETE`; `fullName` можно передать при регистрации или подтверждении. Телефон этим API не поддерживается; неизвестные поля: 400.
- Письмо содержит одноразовую ссылку на экран заполнения профиля, срок 30 минут.
- Повторный запрос для `PENDING_EMAIL` выпускает новый токен и отменяет прежний.
- Для `ACTIVE` и `BLOCKED` аккаунт не меняется и регистрационная ссылка не отправляется.
- Ответ 202 и его сообщение одинаковы для нового, ожидающего, активного и заблокированного аккаунта; ответ не подтверждает доставку письма.
- Повтор письма не чаще раза в минуту; действуют лимиты по `email` и IP, при превышении 429.
- Пароли и токены не возвращаются в `JSON` и не записываются в журнал.

#### 003. Завершить регистрацию: сохранить профиль и пароль, подтвердить email

**`POST`** `/auth/register/confirm`

**Доступ:** Без входа.

**Параметры запроса**

**Тело · `JSON`**

| Параметр / модель | Тип / условия | Обязательно |
| --- | --- | --- |
| `token` | `string` | **Да** |
| `fullName` | `string` | **Да** |
| `password` | `string` | **Да** |
| `accountType` | `TRAINER \| ATHLETE \| PARENT` | — |

**Ответ:** **204** — `без тела`

**Правила**

- Принимается неистёкший неиспользованный токен `REGISTRATION` для аккаунта `PENDING_EMAIL`. Email определяется по токену. `fullName` обязателен и ограничен 200 символами; `password` обязателен, 15–128 символов. `accountType` по умолчанию `ATHLETE`.
- В одной транзакции сервер сохраняет `fullName` и `accountType`, хеширует пароль Argon2id, задаёт `emailVerifiedAt`, переводит аккаунт в `ACTIVE` и погашает токен.
- При ошибке валидации изменения не сохраняются и действующий токен не расходуется.
- Для истёкшего, использованного, заменённого или неподходящего токена возвращается 400.
- Повторное или параллельное подтверждение не активирует аккаунт второй раз.
- Простое открытие ссылки не активирует аккаунт и не погашает токен.
- Успешный запрос возвращает 204 без автоматического входа; пользователь входит через /auth/login.
- Роли, `appRole` и memberships в теле не принимаются.
- Созданный аккаунт имеет `appRole` = `USER`; назначение Membership в этот API не входит.

- view проверяется по ролям членства.

- Журнал исключает пароли/токены и действия над недоступными объектами.

## 7. Примеры и проверка новой регистрации

### 7.1. Последовательность действий

1. Клиент получает `GET /api/v1/auth/csrf` и сохраняет cookie сессии. В изменяющих запросах передаёт токен в заголовке, указанном в `headerName`.
2. На первом экране пользователь вводит только `email`. Клиент отправляет `POST /api/v1/auth/register`.
3. Сервер возвращает `202`. Интерфейс показывает одинаковое сообщение независимо от наличия аккаунта. Ответ означает принятие запроса, а не доставку письма.
4. Пользователь открывает ссылку из письма. Интерфейс показывает форму с именем, телефоном и паролем. Ссылка содержит токен регистрации; маршрут страницы определяется фронтендом и не является новым API-методом.
5. Если ссылка открыта в другом браузере, клиент сначала получает там `CSRF`-токен и cookie через `/auth/csrf`. Регистрационный токен и `CSRF`-токен имеют разные назначения.
6. Пользователь отправляет заполненную форму. Клиент вызывает `/auth/register/confirm`. Открытие страницы само по себе токен не расходует.
7. После `204` интерфейс предлагает войти через `/auth/login`. После входа клиент получает новый `CSRF`-токен.
8. Пока доступ не назначен, `/me` возвращает `organizations: []`. Интерфейс показывает ожидание доступа; саморегистрация не назначает роль или организацию.

### 7.2. Запрос ссылки

`POST /api/v1/auth/register`

```json
{
  "email": "user@example.com"
}
```

Ответ `202` (пример нейтрального сообщения):

```json
{
  "message": "Если регистрация для этого адреса доступна, на него будет отправлено письмо со ссылкой."
}
```

| Поле | Тип | Обязательно | Ограничения |
| --- | --- | --- | --- |
| `email` | string | Да | Корректный адрес; нормализация и уникальность на сервере |
| `accountType` | `TRAINER \| ATHLETE \| PARENT` | Нет | По умолчанию `ATHLETE` |
| `fullName` | string | Нет | Не более 200 символов; можно заполнить и при подтверждении |

`password` и `phone` не принимаются; неизвестные поля отклоняются. Новый аккаунт: `PENDING_EMAIL`, `accountType` по умолчанию `ATHLETE`, `fullName` равен переданному значению или пустой строке, `emailVerifiedAt = null`, без хеша пароля и членств. Повторная отправка заменяет токен, а не создаёт второго пользователя.

### 7.3. Завершение регистрации

`POST /api/v1/auth/register/confirm`

```json
{
  "token": "<одноразовый токен из ссылки>",
  "fullName": "Иван Иванов",
  "password": "<пароль пользователя длиной 15–128 символов>",
  "accountType": "ATHLETE"
}
```

Значения в угловых скобках — обозначения для примера, а не действующие секреты.

| Поле | Тип | Обязательно | Ограничения |
| --- | --- | --- | --- |
| `token` | string | Да | Действующий токен `REGISTRATION`, срок 30 минут, одноразовый |
| `fullName` | string | Да | Непустое имя после удаления пробелов по краям |
| `password` | string | Да | 15–128 символов; без обязательных сочетаний типов символов; не обрезается |
| `accountType` | `TRAINER \| ATHLETE \| PARENT` | Нет | Если отсутствует, сохраняется `ATHLETE` |

Ответ: `204 No Content`. Сессия входа автоматически не создаётся. Email берётся из токена, а не из тела запроса. Повтор пароля, если он предусмотрен интерфейсом, проверяется на клиенте и не передаётся дополнительным полем API.

### 7.4. Ошибки и пограничные случаи

Общий формат ошибки задан в разделе 6.1. Конкретные строковые значения `code` для регистрации в исходнике не заданы и этой редакцией не фиксируются.

| Ситуация | Результат |
| --- | --- |
| Невалидный email или лишние поля первого шага | `400`; запрос регистрации не выполняется |
| Повторная отправка чаще разрешённого лимита | `429` |
| Email уже относится к ACTIVE или BLOCKED | Нейтральный `202`; аккаунт не меняется, регистрационное письмо не отправляется |
| Токен истёк, использован, заменён либо имеет другое назначение | `400`; профиль, статус и пароль не меняются |
| Имя отсутствует или пустое; пароль не соответствует длине | `400`; действующий токен можно использовать после исправления полей |
| Нет корректного CSRF-токена | Запрос отклоняется механизмом CSRF; регистрационный токен не заменяет CSRF-защиту |
| Два запроса подтверждения с одним токеном | Только один успешно завершает регистрацию; второй получает `400` |
| Пользователь открыл ссылку, но не отправил форму | Аккаунт остаётся `PENDING_EMAIL`, токен не расходуется |
| Ошибка отправки SMTP | Ошибка журналируется без токена; `202` не гарантирует доставку, доступна повторная отправка после задержки |

### 7.5. Проверки при реализации

- Первый шаг требует `email`; `accountType` и `fullName` необязательны, а `password` и `phone` не принимаются.
- До подтверждения нельзя войти; `fullName` хранится как переданное значение либо пустая строка, пароль отсутствует.
- Подтверждение без имени или пароля отклоняется; корректный запрос атомарно сохраняет данные, подтверждает `email` и погашает токен.
- Телефон не входит в текущую модель аккаунта; имя после подтверждения обязательно.
- Повторная отправка аннулирует предыдущую ссылку, а истечение 30 минут делает токен недействительным.
- Открытие ссылки почтовым сканером не завершает регистрацию: изменение состояния происходит только при отправке формы.
- Параллельные запросы регистрации одного нормализованного `email` не создают дубликаты; параллельное подтверждение не применяет изменения дважды.
- После успешного входа доступны `/me`, список `/organizations`, создание организации, смена пароля и выход. Создатель новой организации автоматически получает членство `TRAINER`.
- Активный или заблокированный аккаунт нельзя перезаписать повторной регистрацией.
- Пароль и токены отсутствуют в логах, истории действий и ответах API; в базе хранятся только их хеши.
