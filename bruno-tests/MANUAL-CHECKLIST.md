# Ручные сценарии

Запускайте запросы из `manual`, если явно не указано `manual-spec`. Каждый сценарий выполняйте на тестовых данных. Результат фиксируйте: дата, роль, запрос, статус, response и фактическое изменение при повторном GET.

## Регистрация, почта и сессии

1. CSRF → регистрация нового email → письмо → подтверждение с именем и паролем → вход → новый CSRF → `/me`.
2. Повторите подтверждение с тем же токеном: 400. Повторная отправка письма должна аннулировать предыдущую ссылку; истёкший через 30 минут токен должен дать 400. Открытие ссылки без отправки формы не активирует аккаунт.
3. С действующим токеном отправьте пустое имя и короткий пароль: 400. Затем исправьте тело и подтвердите тем же токеном: 204. Неверное тело не должно расходовать токен.
4. В отдельном сеансе браузера/Bruno проверьте вход PENDING_EMAIL и BLOCKED: отказ. ACTIVE и BLOCKED email при повторной регистрации получают одинаковый нейтральный 202 и не меняют профиль; письмо регистрации не должно отправляться.
5. Для сброса пароля получите новый токен из письма. Успешный сброс: 204, старый пароль больше не подходит, прежние сессии теряют доступ. Повтор токена: 400. Регистрационный токен не должен подходить для сброса и наоборот.
6. Смена своего пароля: неверный текущий пароль отклоняется; успешная смена завершает сессии. Проверьте длины нового пароля 14, 15, 128, 129 символов и сохранение значимых пробелов.
7. После выхода `/me`: 401. Изменяющие запросы без CSRF: 403. Cookie должен быть HttpOnly и SameSite=Lax. Проверьте смену идентификатора сессии при входе и абсолютное истечение через 8 часов.
8. Для rate limit используйте отдельный email и соблюдайте задержки, описанные backend. Убедитесь, что после превышения лимита возвращается 429; этот сценарий вынесен из регрессии, чтобы не блокировать обычные прогоны.

## Роли, права и организация

Подготовьте отдельные ACTIVE аккаунты TRAINER, PARENT, ATHLETE и AGENCY, два спортсмена и две организации. Родителя свяжите только с одним ребёнком. Аккаунт ATHLETE свяжите только с его карточкой. В текущем коде административного API назначения произвольных ролей нет: нужные AGENCY-членства и ограничения прав готовятся в тестовой БД; не считать этот setup покрытым коллекцией.

Для смены пользователя сначала выйдите, получите CSRF, войдите с нужными credentials и обновите CSRF. Cookies и runtime-переменные одного аккаунта не переносите в другой сеанс.

| Кто | Проверка | Ожидаемый результат по ТЗ |
| --- | --- | --- |
| TRAINER с read/write | Чтение, создание и изменение разрешённого модуля | Успех; повторный GET отражает изменение |
| TRAINER без нужного права | GET/POST/PATCH данного модуля | 403 |
| PARENT | Свой ребёнок, его начисление, документ, результат | Доступ при нужных read-правах |
| PARENT | Другой ребёнок или его объект | 404; запись отсутствует и в списке/отчёте |
| ATHLETE | Своя карточка и связанные данные | Доступ при нужных read-правах |
| ATHLETE | Чужая карточка | 404 |
| PARENT/ATHLETE | Создание группы, начисления или платежа | 403 |
| PARENT/ATHLETE | Загрузка своего документа и ответ за своего спортсмена | Успех при связи и допустимом состоянии |
| AGENCY | Чтение и экспорт при выданных правах | Успех |
| AGENCY | Изменения, загрузка, ответ и отметка прочтения | Отказ |
| APP_ADMIN без членства | Данные организации | Отказ; административная роль сама не даёт доступ |
| Любой пользователь | Запись другой организации через свой organizationId | 404 |

Проверьте изоляцию также для ID в JSON, query, вложениях, составе групп, итоговых суммах и экспортах. Автоматический E2E проверяет чужие ID между двумя организациями, доступными одному тренеру; сценарии родителя, спортсмена и председателя требуют этой отдельной матрицы.

## Основные операции

1. Создайте справочники sport-types, training-types, venues → секцию → группу с активным тренером → спортсмена → зачисление. ID сохраняются после успешных POST. Повторное зачисление не создаёт вторую открытую запись.
2. В фильтрах проверьте совпадение и отсутствие результатов, границы page/size, несколько страниц и стабильный состав. Просмотр группы с `includeFormer=true` должен показывать завершённые периоды участия.
3. Загрузите PNG из fixtures, затем настоящий PDF и JPEG. Попробуйте TXT, пустой файл, неверный MIME/сигнатуру, файл больше 10 МБ. Они не должны сохраняться; конкретный статус ограничений multipart сверяйте с ТЗ отдельно.
4. Для документа проверьте даты выдачи и окончания, фильтр expired, скачивание и отсутствие доступа к файлу по публичному URL. Произвольное имя файла не должно влиять на путь хранения. Метаданные не должны раскрывать storageName.
5. Создайте опубликованное мероприятие с участником. Родитель/спортсмен отвечает ACCEPTED или DECLINED до дедлайна; после дедлайна изменение ответа отклоняется. Пользователь без связи не может отвечать за чужого участника.
6. Объявление: черновик → получатели → публикация → прочтение → ответ ACCEPTED/DECLINED. После публикации содержание не редактируется. Проверку просмотра истории ответов выполняйте в `manual-spec`, соответствующий GET ещё не реализован.

## Тренировки и финансы

1. Создайте прошедшую тренировку для группы с участниками. Закрытие до отметки всех участников должно отклоняться. После отметок сохраните DRAFT, затем CLOSED: тренировка COMPLETED, последующее изменение отчёта и посещаемости запрещено.
2. Будущую тренировку нельзя закрыть. Отмена без причины отклоняется. Отмена с причиной переводит её в CANCELLED; не должна автоматически отменять начисления.
3. Начисление 1000 → платёж 400 с ключом K → повтор такого же платежа с K. Остаток 600, один платёж 400. Новый платёж 601 отклоняется; платёж 600 с новым ключом закрывает долг.
4. Два клиента одновременно платят больше остатка в сумме: итоговые ACTIVE-платежи не превышают начисление. Это отдельная проверка конкурентности, последовательный Runner её не доказывает.
5. Повторите K с отличающейся суммой: по ТЗ 409. Текущая реализация возвращает прежний платёж без сравнения тела — зафиксируйте расхождение.
6. Аннулирование платежа и отмену начисления проверяйте через `manual-spec`: в текущих контроллерах этих методов нет. После реализации сверяйте пересчёт долга и сохранение истории.

## Отчёты и dashboard

1. Сверьте ATTENDANCE/TRAININGS/PROGRESS/CHARGES с созданными данными и экспортом CSV. Проверьте русские символы, кавычки, запятые, переносы строк, текст с `=`, `+`, `-`, `@` в пользовательских полях.
2. Пользователь без reports.export не должен скачивать отчёт. Без read-права исходного модуля отчёт недоступен. В TRAININGS reportStatus должен быть null без trainingReports.read.
3. Фильтры athlete/group/section/coach, выгрузки PDF/XLSX и предел 10 000 строк сверяйте с `SPEC-GAPS.md`: реализация частичная.
4. Dashboard для TRAINER/PARENT/ATHLETE/AGENCY показывает только доступные данные. Журнал не содержит паролей и токенов. Родительский и спортивный вид с чужим athleteId запрещены.

Статусы и бизнес-ожидания этой матрицы взяты из ТЗ; успешный прогон автоматической коллекции для текущего кода не означает, что вся матрица выполнена.
